# ch14 · 缓冲文件 I/O：`printf` 底下那层，以及缓冲区的存在性实证

> 对应实验：主机侧实测（clang 23.1.0，macOS）
> 对应书：**第 14 章 缓冲文件 I/O**（14.1 printf 函数 / 14.2 ASCII 表 /
> 14.3 读数据 / 14.4 打开文件 / 14.5 二进制 I/O / 14.6 缓冲与刷新）

## 本节讲什么

书这章讲"大型机器"（你的电脑）上的文件 I/O。
对裸机轨来说，价值不在"我会用 `fopen`"，
而在两件事：

1. **理解 `printf` 底下的那层缓冲**——ch09 讲过裸机的 `printf` 要自己接，
   而"接"的就是这里讲的这一层；
2. **文本模式 vs 二进制模式**——这在协议/日志/固件文件里是硬知识。

本篇用一个实测把"缓冲区真的存在"证明给你看（不是靠文档说）。

## 一、缓冲区真的存在吗？看磁盘文件大小（实测）

```c
static long fsz(const char*p){ struct stat st; stat(p,&st); return (long)st.st_size; }
int main(void){
    FILE *f = fopen("buf2.txt","w");
    fprintf(f,"hello");
    printf("fprintf(\"hello\") 之后，磁盘上的文件大小 = %ld\n", fsz("buf2.txt"));
    fflush(f);
    printf("fflush() 之后，磁盘上的文件大小       = %ld\n", fsz("buf2.txt"));
    fprintf(f,"world");
    printf("又写 5 字节不 flush，磁盘大小         = %ld\n", fsz("buf2.txt"));
    fclose(f);
    printf("fclose() 之后，磁盘大小               = %ld\n", fsz("buf2.txt"));
}
```

```
$ clang -O0 -o ch14b ch14b.c && ./ch14b
fprintf("hello") 之后，磁盘上的文件大小 = 0  ← 还没落盘
fflush() 之后，磁盘上的文件大小       = 5
又写 5 字节不 flush，磁盘大小         = 5
fclose() 之后，磁盘大小               = 10
```

**这就是缓冲的直接证据**：写了 5 个字节，文件还是 **0 字节**。
数据在你进程的用户态缓冲区里，没进内核、更没进磁盘。

三个刷新时机：

| 时机 | 何时 |
|---|---|
| **缓冲区满** | 默认 4 KB（或由 `setvbuf` 指定） |
| **`fflush(f)`** | 显式刷新（实测：0 → 5） |
| **`fclose(f)`** | 隐式刷新（实测：5 → 10） |

⚠ **程序崩溃 / 掉电时，缓冲区里的数据全丢。**
这在裸机上的对应物很直接：**UART 的发送缓冲如果没 flush 就复位，日志就少一段。**
调试"最后几行日志不见了"时的第一怀疑对象就是这个。

## 二、文本模式 vs 二进制模式（实测）

```
同一个 int 1000000：二进制 4 字节 / 文本 7 字节
--- 实际文件字节数 ---
4 v.bin
7 v.txt
00000000: 4042 0f00                                @B..
```

| | 大小 | 内容 | 特点 |
|---|---|---|---|
| 二进制 `fwrite(&v, 4, 1, f)` | **4 字节** | `40 42 0f 00`（小端） | 精确、快速、不可读 |
| 文本 `fprintf(f, "%d", v)` | **7 字节** | `1000000` | 可读、可 diff、**慢且大** |

`0x000F4240` = 1000000。`40 42 0f 00` 是它的**小端**字节序
（Cortex-M 也是小端，ch08 实测过 `u.i=0x12345678 → b[0]=0x78`）。

**换行符的差异**（这才是 `t` / `b` 的真正区别）：

| 平台 | 文本模式写 `\n` | 二进制模式写 `\n` |
|---|---|---|
| Linux / macOS | `\n`（1 字节） | `\n` |
| **Windows** | **`\r\n`（2 字节）** | `\n` |

所以：**只有在 Windows 上 `"w"` 和 `"wb"` 才有区别**，
但这个区别足以毁掉一个固件文件（多出来的 `\r` 让校验失败）。

**规则**：**凡是"数据"一律用 `b`，只有"给人看的文本"才用 `t`。**
固件镜像、协议报文、配置文件、日志文件——都用 `b`。

## 三、这跟裸机有什么关系

书这一章跑在 PC 上，但它的概念直接映射回板子：

| 文件 I/O 概念 | 裸机对应 |
|---|---|
| `FILE *` + 缓冲区 | `uart1_putc` 外面套一层输出缓冲（ch09） |
| `fflush()` | 把缓冲里的字节真的发完（或等 TXE） |
| 文本 vs 二进制 | 日志用 ASCII，协议用二进制（ch06 讲过字节序） |
| `fwrite(&x, sizeof x, 1, f)` | 直接把结构体按字节发出去（注意对齐！ch08） |
| 缓冲满了才写 | 攒够 N 字节再发，减少 per-byte 开销 |

**裸机上最常见的"缓冲"实现**（ch09 的进阶版）：

```c
static char g_tx_buf[128];
static unsigned g_tx_len;

void log_putc(char c){
    g_tx_buf[g_tx_len++] = c;
    if (g_tx_len >= sizeof(g_tx_buf) || c == '\n') log_flush();
}
void log_flush(void){
    for (unsigned i = 0; i < g_tx_len; i++) uart1_putc(g_tx_buf[i]);
    g_tx_len = 0;
}
```

⚠ 和 `FILE*` 一样的教训：**`log_putc` 之后不 `log_flush`，
数据就在 RAM 里，掉电/复位就没了。** 出 HardFault 时最想要的那几行日志，
恰恰就是没 flush 的那几行。

**对策**：关键日志（错误、断言失败）**立即 flush**，
普通日志可以攒着。或者干脆让 HardFault handler 自己调 `log_flush()`。

## 四、与 PC / LDD- 侧的对照

| 概念 | PC / Linux | 裸机 STM32 |
|---|---|---|
| `stdout` 缓冲 | 行缓冲（tty）/ 全缓冲（管道） | 没有 `stdout`，自己实现 |
| 刷新 | `fflush` / `fclose` / 缓冲满 | 同上，但**掉电就是丢** |
| 文本/二进制差异 | Windows 上 `\n` → `\r\n` | 无（但协议层要注意） |
| `printf` 格式化 | libc 全功能 | 自己写 `mini_printf`（ch09） |
| 文件 | 有文件系统 | 通常没有；要么 Flash 页（ch11），要么外挂 SPI Flash/SD |

## 五、最小可跑

```c
#include <stdio.h>
int main(void){
    /* ① 二进制写：精确、快 */
    int v = 1000000;
    FILE *fb = fopen("v.bin", "wb");
    fwrite(&v, sizeof v, 1, fb);
    fclose(fb);                        /* fclose 会隐式 fflush */

    /* ② 文本写：可读、大、慢 */
    FILE *ft = fopen("v.txt", "w");
    fprintf(ft, "%d", v);
    fclose(ft);

    /* ③ 关掉缓冲（调试/日志场景） */
    setvbuf(stdout, NULL, _IONBF, 0);  /* 无缓冲：每次 printf 立刻写 */
    /* 或行缓冲：_IOLBF —— 遇到 \n 就 flush，最像"打日志"的语义 */

    /* ④ 读回来（必须检查返回值！） */
    int r = 0;
    FILE *g = fopen("v.bin", "rb");
    if (g && fread(&r, sizeof r, 1, g) == 1) printf("%d\n", r);
    if (g) fclose(g);
    return 0;
}
```

## 坑点（原书怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "写了就进文件了" | **没有**。实测 `fprintf("hello")` 之后磁盘文件是 **0 字节**，`fflush` 之后才变 5 |
| "`fclose` 只是关闭" | 它**隐式 fflush**。实测 `fclose` 后 5 → 10 字节 |
| "文本和二进制差不多" | 实测同一个 int：二进制 4 字节 vs 文本 7 字节。Windows 上 `t` 模式还会把 `\n` 变成 `\r\n` |
| "`printf` 很便宜" | 格式化 + 系统调用 + 缓冲管理，一次可能几千个周期。裸机上要谨慎（ch09） |
| "忘了 `fclose` 只是泄漏一个句柄" | 还可能**丢数据**（缓冲没刷）。实测"又写 5 字节不 flush"时磁盘仍是 5 |
| "二进制文件不可移植" | 是（字节序、类型大小都不同平台有差异，ch04 实测 `long` 在 Mac 是 8、Cortex-M 是 4）。跨平台的二进制格式要**显式定义**每个字段的宽度和字节序 |
| "裸机上用不了这章" | 概念全都用得上：缓冲、flush、文本 vs 二进制、按字节序列化 |

## 衔接

- **ch09（串口）**：`printf` 的裸机实现接的就是本章这一层。
- **ch10（中断）**：串口发送用中断时，缓冲区的存在是必须的（ISR 从缓冲取字节）。
- **ch11（链接器）**：日志字符串在 `.rodata`，占 Flash。
- **ch15（原始 I/O）**：本章是"带缓冲的 I/O"，下章是"不带缓冲的 raw I/O"
  ——对照着看才明白缓冲层在做什么。
- **ch16（浮点）**：`%f` 的格式化是最贵的 `printf` 特性。
- **LDD- 侧**：内核的 `struct file` + `file_operations` + page cache，
  就是本章这套东西的内核版；`fsync()` 对应 `fflush()`。

## 代码自测

<details>
<summary>Q1：为什么 `fprintf` 之后文件还是 0 字节？数据去哪了？</summary>

在你的进程的**用户态缓冲区**里。

层次是这样的：

```
你的程序: fprintf(f, "hello")
   ↓
stdio 缓冲区（用户态，默认 4 KB）  ← "hello" 停在这里
   ↓  （只有缓冲满 / fflush / fclose 时才往下走）
内核: write(2) 系统调用
   ↓
内核页缓存（page cache）
   ↓  （由内核的回写线程决定何时落盘，或 fsync 强制）
磁盘
```

实测证据：

```
fprintf("hello") 之后，磁盘上的文件大小 = 0  ← 还没落盘
fflush() 之后，磁盘上的文件大小       = 5
fclose() 之后，磁盘大小               = 10
```

所以 `fprintf` 返回成功**不代表数据已经到磁盘**，
只代表"进了 stdio 缓冲区"。

**为什么要这么设计**：系统调用很贵（几百到几千个周期）。
如果每个字符都 `write()` 一次，写 1 KB 就是 1024 次系统调用。
攒够 4 KB 再写，系统调用次数降到 1/4096。

**代价与对策**：

| 风险 | 对策 |
|---|---|
| 崩溃/掉电丢数据 | 关键数据后立即 `fflush`（或 `fsync` 到磁盘） |
| 日志顺序错乱（多进程/线程） | 每个写者独立 FILE，或写前 flush |
| 交互式程序看不到输出 | 行缓冲 `setvbuf(f, NULL, _IOLBF, 0)`，或显式 flush |

裸机上的对应：UART 输出缓冲同理，
**调试时建议"错误日志立即 flush，普通日志攒着"**，
并且 HardFault handler 里第一件事就是 flush。
</details>

<details>
<summary>Q2：`"w"` 和 `"wb"` 到底差在哪？我该默认用哪个？</summary>

**在 Linux/macOS 上：没区别。** 在 Windows 上：差一个字符。

| 平台 | 文本模式写 `\n` | 二进制模式写 `\n` |
|---|---|---|
| Linux / macOS | `\n`（0x0A，1 字节） | `\n` |
| Windows | **`\r\n`（0x0D 0x0A，2 字节）** | `\n` |

读的时候也对称：Windows 文本模式读到 `\r\n` 会合并成 `\n`。

**为什么这很重要**：如果你在 Windows 上用 `"w"` 写一个固件镜像、
一个 PNG、或者任何二进制格式，每个 `0x0A` 字节前面都会被插入一个 `0x0D`——
文件就坏了，而且校验和会对不上。

**规则**：

```
给人看的文本（日志、配置文件、CSV）→ "w" / "r"
其他一切（固件、协议报文、图片、序列化数据）→ "wb" / "rb"
```

更稳的做法是**一律用 `b`**——即使是文本。
因为文本模式唯一提供的"换行符翻译"在跨平台时往往是**麻烦**而不是帮助。
很多项目的规范就是"所有 `fopen` 都带 `b`"。

顺带一个相关问题：**`strlen` 和文件大小的差 1**。
ch06 实测 `sizeof("abc") = 4` 而 `strlen("abc") = 3`。
写字符串时 `fwrite(s, 1, strlen(s), f)` 写的是 3 字节（不含 `\0`）；
`fwrite(s, 1, sizeof(s), f)` 对**数组**才对（会把 `\0` 也写进去）。
裸机上序列化字符串时，通常写"长度 + 内容"，或者"内容 + `\0` 结束符"，
两者要选一个并写进协议文档。
</details>

<details>
<summary>Q3：`fwrite(&v, sizeof v, 1, f)` 有什么隐患？</summary>

它把**内存里的位模式**原样写到文件——这意味着文件格式
和"当前平台的类型表示"绑定了。三个隐患：

**① 类型宽度**（ch04 实测）

```
Mac (arm64):      sizeof(long) = 8
Cortex-M3:        sizeof(long) = 4
```

用 `long` 序列化的文件，在两个平台间不可互换。**要写 `uint32_t`。**

**② 字节序**（ch08 实测）

```
u.i = 0x12345678 → b[0]=0x78 b[1]=0x56   （小端）
```

Cortex-M 是小端，x86/arm64 也是小端，但**网络协议和一些 MCU 是大端**。
跨设备传输必须显式定义。

**③ 结构体填充**（ch08 实测）

```
struct S1 { char a; int b; char c; };   → sizeof = 12（有 6 字节填充）
```

直接 `fwrite(&s, sizeof s, 1, f)` 会把**填充字节也写进去**，
而填充字节的内容是**未初始化的**（可能是任意值）。
后果：同样的数据，两次写出的文件字节不同（校验和对不上），
而且泄漏了内存里的残留数据。

**正确做法**：显式序列化。

```c
/* 写：逐字段、定宽、定字节序 */
void write_u32_le(FILE *f, uint32_t v){
    uint8_t b[4] = { v, v>>8, v>>16, v>>24 };
    fwrite(b, 1, 4, f);
}
void write_msg(FILE *f, const msg_t *m){
    write_u32_le(f, m->id);
    write_u32_le(f, m->len);
    fwrite(m->payload, 1, m->len, f);   /* payload 是 unsigned char[]，无填充 */
}

/* 读：对称地逐字段读 */
uint32_t read_u32_le(FILE *f){
    uint8_t b[4];
    if (fread(b, 1, 4, f) != 4) return 0;    /* 必须检查返回值！ */
    return (uint32_t)b[0] | ((uint32_t)b[1]<<8)
         | ((uint32_t)b[2]<<16) | ((uint32_t)b[3]<<24);
}
```

这就是 ch08 Q3 讲的"字节流协议用显式读写函数"在文件 I/O 上的同一个原则。
</details>

<details>
<summary>Q4：裸机上没有文件系统，这章还有什么用？</summary>

概念全都有用，只是载体从"文件"变成"字节流"。

| 本章概念 | 裸机上的落点 |
|---|---|
| **缓冲** | UART 发送/接收缓冲（ch09、ch10）。攒够再发，减少 per-byte 开销 |
| **flush** | 关键日志立即发出；HardFault handler 里第一件事 |
| **文本 vs 二进制** | 日志用 ASCII（人读），协议用二进制（机器读） |
| **按字段序列化** | ch08 的 `rd_be32/rd_le32`，直接就是本章 Q3 的代码 |
| **返回值检查** | `fread` 的返回值 vs `uart_getc` 返回 -1 表示无数据 |

而且**裸机上"有文件系统"的场景比你想象的多**：

- **SPI Flash / SD 卡 + FATFS**：数据记录器、固件升级（OTA）都要；
- **内部 Flash 当小文件系统**：存配置、校准值（ch11 讲过）；
- **USB Mass Storage**：把板子模拟成 U 盘。

这时候本章的知识就直接用上了——只是 `FILE*` 换成了 `FIL*` (FATFS)，
`fopen/fread/fwrite` 换成 `f_open/f_read/f_write`，语义完全一样。

**最有价值的一条是"缓冲与刷新"的心智模型**：
理解了"写成功 ≠ 数据到了目的地"，
就能理解为什么裸机上 HardFault 时最后几行日志会丢、
以及为什么关键日志要立即 flush。
</details>

<details>
<summary>Q5：`printf` 到底有多贵？裸机上该怎么用？</summary>

**贵在三处：格式化、缓冲管理、底层 I/O。**

格式化是最贵的部分，尤其是浮点：

| 格式 | 大致代价 |
|---|---|
| `%s` / `%c` | 便宜（拷贝） |
| `%d` / `%u` | 中等（除法：M0/M3 没有硬件除法器时，`/10` 是软件实现） |
| `%x` | 中等（移位，比除法快） |
| **`%f`** | **很贵**（软件浮点 + 格式化，M3 上一次几百微秒） |

实测参考（ch04）：M3 没有 FPU，实测符号表里出现过 `__aeabi_dadd`/`__aeabi_dmul`
——浮点运算是**库函数调用**，不是几条指令。

**在 8 MHz 的 F103 上估个量级**：

| 操作 | 时间 |
|---|---|
| `uart1_putc`（轮询，115200） | ~87 μs/字节（受波特率限制） |
| `mini_printf("%d", x)` | 几十 μs |
| `printf("%f", x)`（软件浮点） | **几百 μs ~ ms** |

**所以裸机上的 `printf` 使用准则**：

1. **ISR 里绝对不用**（ch10 讲过：会丢中断）；
2. **实时路径上不用**（控制循环里打日志 = 破坏时序）；
3. **发布版裁掉**：用 `#if LOG_LEVEL`（ch12）把日志编译掉，省 Flash 省时间；
4. **避免 `%f`**：要么转成整数打（比如温度 ×100 打 `2345` 表示 23.45℃），
   要么只在调试期用；
5. **缓冲 + 分级**：攒着发，错误级立即 flush；
6. **考虑 ITM/SWO**（ch09 提过）：调试期用 SWO 输出，
   不占用 UART、速度快得多，且发布版没有副作用。

**一句话**：日志是**调试工具**，不是产品功能。
它的存在不应该影响系统的时序和可靠性。
</details>
