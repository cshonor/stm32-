# ch07 · 局部变量与函数：栈帧、递归，以及"20 KB 够不够"

> 对应实验：主机侧实测（clang 23.1.0，`--target=armv7m-none-eabi -mcpu=cortex-m3`）
> 对应书：**第 7 章 局部变量和函数**（7.1 局部变量 / 7.2 隐藏变量 / 7.3 函数 /
> 7.4 栈帧 / 7.5 递归 / 7.6 编程风格）

## 本节讲什么

在 PC 上，"局部变量"是个不需要思考的概念：函数进来就有，返回就没。
在裸机上它变成一个**必须预算的资源**，因为：

- 栈的大小是**链接脚本里写死的一行**（`_estack = ORIGIN(RAM) + LENGTH(RAM)`）；
- **没有 MMU、没有守卫页**，栈溢出不会报错，只会静静踩掉 `.bss`/`.data`；
- 递归的深度直接决定会不会爆栈，而这个数字**可以算出来**。

本篇用两个实测把这件事量化：

1. `clang -fstack-usage` 生成每函数的栈用量；
2. 反汇编看栈帧是怎么建/拆的，以及 `-Os` 怎么把递归变成循环。

## 一、`-fstack-usage`：把"栈用了多少"变成一张表（实测）

```c
/* ch07.c */
int leaf(int a, int b){ volatile int t = a + b; return t; }
int with_locals(int n){ int buf[8]; int i; int s=0;
    for(i=0;i<8;i++) buf[i]=n+i;
    for(i=0;i<8;i++) s+=buf[i];
    return s; }
int fact(int n){ return (n<=1) ? 1 : n*fact(n-1); }
int deep(int n){ if(n==0) return 0; return 1+deep(n-1); }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -fstack-usage -c ch07.c
$ cat ch07.su
ch07.c:1:leaf         4    static
ch07.c:2:with_locals  32   static
ch07.c:6:fact          0   static     ← 0？见下面
ch07.c:7:deep          0   static
```

```
$ # 换成 -O0 再来一遍
$ clang ... -O0 -fstack-usage -c ch07.c -o ch07_O0.o && cat ch07_O0.su
ch07.c:1:leaf         12   static
ch07.c:2:with_locals  44   static
ch07.c:6:fact         24   static     ← 真递归，每帧 24 字节
ch07.c:7:deep         16   static
```

两张表对比，三件事浮出来：

1. **优化级别直接改变栈用量**：`leaf` 4 → 12 字节，`with_locals` 32 → 44 字节。
   `-Os` 会复用寄存器、不保存用不到的寄存器。
2. **`fact` 在 `-Os` 下是 0，在 `-O0` 下是 24**——
   这不是"递归不占栈"，是**编译器把递归改成了循环**（下面用反汇编确认）。
3. `-fstack-usage` 报的是**单帧**大小，不含递归深度。递归的总开销要自己乘。

## 二、栈帧长什么样（实测反汇编）

### 2.1 有局部数组的函数

```
$ llvm-objdump -d ch07.o       # -Os
0000000c <with_locals>:
       c: b088          sub  sp, #0x20          ← 一进来就减 32 字节
       e: 2200          movs r2, #0
      10: 4669          mov  r1, sp             ← r1 = 数组基址（就是 sp）
      14: 1883          adds r3, r0, r2
      16: f841 3022     str.w r3, [r1, r2, lsl #2]
      1a: 3201          adds r2, #1
      1c: 2a08          cmp  r2, #8
      1e: d1f9          bne  0x14
      ...
      30: b008          add  sp, #0x20          ← 返回前加回去
      32: 4770          bx   lr
```

`sub sp, #0x20` / `add sp, #0x20` 这一对就是**栈帧的建立与销毁**，
32 字节正好等于 `buf[8]`（8 × 4）`.su` 报的也是 32——**对上了**。

注意：**没有 `push {..., lr}`**。因为 `with_locals` 不再调用别人（叶子函数），
`lr` 不用保存。这是 Cortex-M 上很常见的优化。

### 2.2 递归：`-Os` 把它变成了循环

```
00000034 <fact>:
      34: 2802          cmp  r0, #2
      36: bfbc          itt  lt
      38: 2001          movlt r0, #1
      3a: 4770          bxlt lr
      3c: 4601          mov  r1, r0
      3e: 2001          movs r0, #1
      40: 4348          muls r0, r1, r0        ← 循环体里做乘法
      42: 2902          cmp  r1, #2
      44: f1a1 0101     sub.w r1, r1, #1
      48: d8fa          bhi  0x40              ← 往回跳，不是 bl 自己
      4a: 4770          bx   lr
```

**没有 `bl fact`**——这是一个普通的循环（`bhi` 往回跳）。
clang 识别出 `fact(n) = n * fact(n-1)` 这种"累加型递归"可以改成迭代，
于是栈用量归零。这就是为什么 `.su` 报 0。

### 2.3 递归：`-O0` 下是真的递归

```
0000006c <fact>:
      6c: b580          push {r7, lr}          ← 保存返回地址
      6e: b084          sub  sp, #0x10         ← 再减 16
      70: 9003          str  r0, [sp, #0xc]
      ...
      86: f7ff fffe     bl  0x86 <fact+0x1a>   ← 真的调用自己
      ...
      96: b004          add  sp, #0x10
```

`push {r7, lr}`（8 字节）+ `sub sp, #0x10`（16 字节）= **24 字节/帧**，
和 `-O0` 的 `.su` 完全对上。

## 三、算一笔账：20 KB 栈能递归多深？

NUCLEO-F103RB：RAM 20 KB，`_estack = 0x20005000`，
实际可给栈用的还要扣掉 `.data`（4）+ `.bss`（8）+ `.noinit`（4）= 约 20 KB − 16 B。

| 函数 | 单帧（实测） | 20 KB 栈能递归多深 |
|---|---|---|
| `fact` @ -O0 | 24 B | 20480 / 24 ≈ **853 层** |
| `deep` @ -O0 | 16 B | 20480 / 16 ≈ **1280 层** |
| `fact` @ -Os | 0 B（变循环） | **无限**（不占用栈） |
| `with_locals` @ -Os | 32 B | 非递归，单次 32 B |

而且 `int` 溢出比栈溢出先到：`fact(13)` 就超过 `INT_MAX` 了（`13! ≈ 6.2e9`）。
**这说明一个重要的工程结论：在 20 KB RAM 的芯片上，递归几乎总是错误的设计。**
不是因为不能跑，而是因为**深度不可控**——
你没法静态证明"这个递归最多 100 层"，一旦输入来自外部（协议包、用户输入），
栈就是个定时炸弹。

裸机的常规做法是：**要么改成迭代，要么显式限制深度**。

## 四、"隐藏变量"：编译器替你造的局部变量

书 7.2 讲 *hidden variables*——你没写，但编译器生成了。裸机上最典型的两类：

| 隐藏变量 | 什么时候出现 | 代价 |
|---|---|---|
| 保存 `lr` / 被调用者保存寄存器 | 函数里还调了别的函数 | `push` 进栈，占用栈帧 |
| 大结构体赋值的临时缓冲 | `struct_big a = b;` | 可能生成 `memcpy` 调用（ch01 实测 `__aeabi_memcpy`） |
| 软件浮点的临时量 | M0/M3 上用 `double` | 栈 + 大量代码（Flash） |

ch01 实测的这行就是这个：

```
U __aeabi_memcpy      ← struct big 整体赋值，编译器替你写了 memcpy 调用
```

## 五、与 PC / LDD- 侧的对照

| 概念 | PC / Linux | 裸机 STM32 |
|---|---|---|
| 栈大小 | 默认 8 MB，可 `ulimit` 调 | 链接脚本写死（本仓库 20 KB 的一部分） |
| 栈溢出 | SIGSEGV + 内核 guard page | **静默**，踩 `.bss`/`.data` |
| 递归 | 随便用 | **几乎不用**，深度不可静态证明 |
| 栈用量分析 | 有 valgrind / `-fstack-usage` | `-fstack-usage` + 手工核算（本篇实测） |
| 局部变量放哪 | 栈（或寄存器） | 同。但大数组要考虑放静态区，别压栈 |
| 返回地址 | 栈上，有 shadow stack 等保护 | 栈上的 `lr`，被踩了就 HardFault |

## 六、最小可跑

```c
/* 递归 → 迭代：把"深度不可控"变成"栈用量固定" */
int fact_iter(int n){          /* -O0 下也只有一帧 */
    int r = 1;
    while (n > 1) { r *= n; n--; }
    return r;
}

/* 大数组别放栈：放静态区（进 .bss，链接脚本负责） */
static int samples[256];       /* ← 1 KB，放 .bss，不占栈 */

/* 需要"每调用一次一份"的大缓冲，才放栈，并且要算清楚 */
void parse(void){
    char line[64];             /* 64 B，可接受 */
    /* char big[4096];   ← 4 KB 在 20 KB RAM 上是灾难 */
}

/* 显式限制深度（如果非要递归） */
int tree_depth_limited(Node *n, int budget){
    if (n == NULL || budget <= 0) return 0;
    int l = tree_depth_limited(n->left,  budget - 1);
    int r = tree_depth_limited(n->right, budget - 1);
    return 1 + (l > r ? l : r);
}
```

## 坑点（原书怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| 书 7.5 讲递归是正常手段 | 在 20 KB RAM 的 MCU 上**几乎不该用**。实测 `-O0` 下 `fact` 每帧 24 B，20 KB 只够 853 层，而深度通常无法静态证明 |
| "编译器会帮我优化递归" | **有时是，不保证**。实测 `-Os` 下 `fact` 变成循环（栈 0），但 `-O0` 下是真递归（24 B/帧）。**不能依赖优化器的心情** |
| "栈够不够跑一下就知道" | 栈溢出**不报错**。要靠 `-fstack-usage` 静态算 + 调试器看 `msp` 的实际水位（ch03 实测：msp 比 `_estack` 低 128 B） |
| "局部变量随便声明" | 大数组（几百字节以上）压栈会吃掉大量预算。实测 `with_locals` 的 `buf[8]` 就吃掉 32 B |
| "结构体赋值是原子的" | 可能生成 `memcpy` 调用（ch01 实测 `__aeabi_memcpy`），既占 Flash 又占栈 |
| "函数不调别人就不用保存 lr" | 对：实测 `with_locals`（叶子）只有 `sub sp`，没有 `push {lr}`；而 `fact`（-O0）有 `push {r7, lr}` |
| "`-fstack-usage` 报 0 就是不用栈" | 只说明**单帧**为 0。递归的总量要乘深度，工具不帮你算 |

## 衔接

- **ch08（复杂数据类型）**：结构体传参/返回时的栈开销，以及"返回大结构体"为什么危险。
- **ch10（中断）**：中断会**在被打断的栈上再压一帧**（8 个寄存器 + 对齐），
  所以栈预算要按"最深调用链 + 中断帧"来算，不是只算主循环。
- **ch11（链接器）**：`_estack` 从哪来、栈溢出的 `ASSERT` 怎么写在链接脚本里。
- **ch19（SysTick）**：`stack_probe` + 填充模式（0xDEADBEEF）实测水位，
  是比静态计算更可靠的方式。
- **LDD- 侧**：内核栈只有 8 KB（或 16 KB），比用户态的 8 MB 小三个数量级——
  所以内核里也禁止深递归。裸机和内核在这个约束上是同一类问题。

## 代码自测

<details>
<summary>Q1：为什么 `-Os` 下 `fact` 的栈用量是 0？递归不需要栈吗？</summary>

递归**本来**需要栈，但 clang 在这个例子里把它消除了。

看实测反汇编：`-Os` 版的 `fact` 里**没有 `bl fact`**，
而是一个 `bhi 0x40` 往回跳的普通循环：

```
      40: 4348   muls r0, r1, r0        ← 循环体
      44: f1a1 0101 sub.w r1, r1, #1
      48: d8fa   bhi  0x40              ← 往回跳（不是调用）
```

这是因为 `fact(n) = n * fact(n-1)` 属于**累加型递归（accumulating recursion）**：
递归调用是函数体里的**最后一个操作**（`return` 的一部分），
且不需要保留当前帧的任何状态。编译器可以把"递归"改写成"循环 + 累加器"。

`-O0` 下（不优化）就是真的递归，实测有 `bl` 调用自己 + `push {r7, lr}`。

**关键教训**：你观察到的"栈用量 0"是**优化器的产物，不是语言性质**。
换一个编译器、换一个优化级别、或者递归形式稍微复杂一点（二叉树递归、两个递归调用），
消除就失效了。

所以工程规则是：**不要依赖编译器消除递归。要么自己写成迭代，要么显式限制深度。**
</details>

<details>
<summary>Q2：`-fstack-usage` 报的是单帧，那整条调用链怎么算？</summary>

手工加，或者用工具。三种做法，成本从低到高：

**① 手工累加（最常用）**
沿着"最深的那条调用路径"把 `.su` 里的数字加起来：

```
main → parse → read_byte → uart_getc
 8  +  32   +    16      +    24     = 80 字节
```

再加上**中断帧**（Cortex-M 自动压 8 个寄存器 = 32 字节，可能还有对齐到 8 字节），
以及浮点上下文（如果用了 FPU，M4 上再多 136 字节）。

**② 链接期汇总**
把 `.su` 文件收起来算"最坏路径"有现成脚本思路：
对每个函数，栈用量 = 自身 + max(它调用的所有函数的用量)，
这是一个图上求最长路径的问题。LLVM 有 `-Wframe-larger-than=` 能直接对单帧报警：

```
clang -Wframe-larger-than=256 ...
```

**③ 运行时实测水位（最可靠）**
在启动时把整个栈区填成魔数（如 `0xDEADBEEF`），
跑一段时间后从栈顶往下扫，看魔数被改到哪——那就是历史最高水位。
ch03 实测过类似的思路（读 `msp` 看到差 128 B）。

**本仓库选 ① + ③**：`make check-stack` 读 `.su`（ch01 已有），
真机上用魔数填充看水位（ch19 补）。
</details>

<details>
<summary>Q3：栈溢出为什么"不报错"？</summary>

因为**没有任何硬件或软件在检查**。

Linux 用户态有三重保护（本篇"对照"表里列了）：MMU 的守卫页、
ASan 的 redzone、分配器的金丝雀。**裸机上一个都没有**：

- Cortex-M（M0/M3/M4）**没有 MMU**，所有地址都是真实的物理地址，
  写哪儿都"成功"；
- 栈往下长，紧挨着的就是 `.bss` 和 `.data`（ch03 实测的段表：
  `.data` @ 0x20000000、`_estack` = 0x20005000）。
  栈指针越过 `.bss` 顶端之后，写的就是别人的变量；
- 没有"栈指针低于某个值就触发异常"的机制——
  （M33/M55 有 Stack Limit 寄存器，`__stack_limit` + HardFault，
  但 F1 的 Cortex-M3 没有）。

后果链条：

```
栈溢出 → 踩 .bss/.data → 某个全局变量变成奇怪的值 → 程序行为异常
       或踩到栈上保存的 lr → 函数返回跳到非法地址 → HardFault
```

第二种还算好查（有明确的 HardFault），第一种是噩梦。

**对策**（按有效性排序）：
1. 静态算（`-fstack-usage` + 最深路径）；
2. 运行时水位（魔数填充）；
3. 链接脚本里把栈放在 RAM 的**最低端**并留一段"栈溢出哨兵"区（ch11）；
4. `.bss` 放在栈的上方而不是下方，让溢出先踩到不那么关键的区域。
</details>

<details>
<summary>Q4："隐藏变量"在裸机上有哪些？为什么要在意？</summary>

书 7.2 说的 hidden variable 就是"你没写但编译器生成的东西"。
在裸机上，它们是**隐形的栈和 Flash 开销**。实测见过的三类：

| 隐藏变量 | 触发条件 | 实测证据 |
|---|---|---|
| 保存 `lr` 和被调用者保存寄存器 | 函数里还调了别人 | `fact` @ -O0 有 `push {r7, lr}`（8 B）；叶子函数没有 |
| `memcpy` 的临时调用 | 大结构体整体赋值 | ch01 实测符号表里的 `U __aeabi_memcpy` |
| 软件浮点的临时量 | M0/M3 上用 `float`/`double` | ch01 实测 `U __aeabi_dadd`、`__aeabi_dmul` |

为什么要在意：

1. **栈预算**：`push {r7, lr}` 每个非叶子函数都可能有，
   深调用链上累积起来不小；
2. **Flash 预算**：`__aeabi_memcpy` 这类库函数会被链接进来，
   实测它们会进最终镜像，白白占 Flash（ch01 的 296 字节里就有这类东西）；
3. **性能**：软件浮点在 M3 上一次 `double` 乘法是几十条指令，
   在 ISR 里用就是灾难（ch10）。

怎么看见它们：

```
llvm-nm -n blink_asm.elf     # 看 U 开头的未定义符号 = 编译器替你要的
llvm-objdump -d xxx.o        # 看 push/sub sp 的实际指令
-fstack-usage                # 看每函数栈用量
```

**原则**：在裸机上，"编译器替你做的事"不是免费的，
每一件都要在栈、Flash 或时间上记账。
</details>

<details>
<summary>Q5：那我到底该怎么决定"这个变量放栈还是放静态区"？</summary>

一条判据 + 一条补充。

**判据：这个变量的生命周期是"一次调用"还是"整个程序"？**

| 放栈（局部） | 放静态区（`.bss`/`.data`） |
|---|---|
| 每次调用都要一份新的 | 全局只有一份 |
| 函数返回就没了 | 程序活着就在 |
| 典型：临时缓冲、循环变量、解析中间量 | 典型：驱动状态、环形缓冲区、配置、统计计数 |

**补充：大小。** 在 20 KB RAM 上，**单个局部数组超过 ~128 字节就要停下来想一想**。

```c
void f(void){
    char small[32];        /* 可以：32 B */
    char medium[256];      /* 慎：占 1/80 的 RAM，且调用链上只能有它一个 */
    char big[4096];        /* 不行：静态区也才 20 KB */
}
static char big[4096];     /* 改静态：进 .bss，编译期就能从 map 文件看到总量 */
```

放静态区的代价是**不可重入**：

- 递归 / 中断嵌套调用同一个函数时，静态缓冲会被覆盖；
- 多线程（FreeRTOS，ch20）下更是直接冲突。

所以完整的决策表是：

| | 小（< 128 B） | 大（> 128 B） |
|---|---|---|
| 需要每调用一份 | ✅ 栈 | ⚠ 栈（但要先算清预算）或改用池 |
| 全局一份就够 | 静态 | ✅ 静态，并注意重入 |
| 会被中断/多任务共享 | —— | ✅ 静态 + 临界区保护（ch10/ch20） |
</details>
