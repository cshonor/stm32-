# ch19（补充篇）· SysTick 与定时器：裸机的"时间"从哪来

> 对应实验：`stm32/06-timer`（⬜ 待建）；本篇的机制部分参照 ARM CMSIS 与 RM0008
> **⚠ 本书 18 章里没有这一章**——这是书外补充，因为"时间"是裸机的刚需
> （去抖、延时、超时、调度全靠它），而书里完全没有讲

## 本节讲什么

前 18 章里，程序只有两种时间观：

- **没有时间**：写完就跑完（`main` 里的初始化）；
- **忙等**：`for (i=0;i<10000;i++);`（ch05 讲过这不可靠）。

但真实的需求全都需要时间：

| 需求 | 需要什么 |
|---|---|
| 按键去抖 | "按下后 20 ms 再看一次" |
| LED 闪烁 | "每 500 ms 翻转一次" |
| 串口超时 | "3 个字符时间内没收到就认为一帧结束" |
| 传感器采样 | "每 10 ms 读一次" |
| RTOS 心跳 | "每 1 ms 做一次调度检查"（ch20） |

裸机上**没有操作系统给你 `sleep()`**，时间是自己造出来的。
本篇讲三种做法，从简单到正确。

## 一、SysTick：Cortex-M 内核自带的"心跳"

**SysTick 是 ARM 内核的一部分，不是 ST 的外设**——
这意味着所有 Cortex-M 芯片都有它，代码可移植。

四个寄存器：

| 寄存器 | 地址 | 作用 |
|---|---|---|
| `SYST_CSR` | `0xE000E010` | 控制与状态（使能、中断使能、时钟源、计数到 0 标志） |
| `SYST_RVR` | `0xE000E014` | 重载值（计数到 0 后自动装回这个值） |
| `SYST_CVR` | `0xE000E018` | 当前值（写任意值清零） |
| `SYST_CALIB` | `0xE000E01C` | 校准值（不一定准，慎用） |

工作方式是**向下计数**：

```
CVR 从 RVR 开始递减 → 减到 0 → （可选）触发中断 → 自动装回 RVR → 继续
```

### 1.1 配置成 1 ms 心跳

```c
#define SYST_CSR (*(volatile uint32_t *)0xE000E010u)
#define SYST_RVR (*(volatile uint32_t *)0xE000E014u)
#define SYST_CVR (*(volatile uint32_t *)0xE000E018u)

static volatile uint32_t g_ms;      /* 毫秒计数（uint32_t 约 49.7 天回绕） */

void systick_init_1ms(uint32_t cpu_hz){
    SYST_RVR = (cpu_hz / 1000u) - 1u;    /* 重载值：1 ms */
    SYST_CVR = 0;                         /* 清当前值 */
    SYST_CSR = (1u << 2)                  /* CLKSOURCE: 1=CPU 时钟 */
             | (1u << 1)                  /* TICKINT:   1=计数到 0 触发中断 */
             | (1u << 0);                 /* ENABLE */
}

void SysTick_Handler(void){               /* 名字是硬件约定的，不能改 */
    g_ms = g_ms + 1u;                     /* ISR 里只做这一件事 */
}
```

NUCLEO-F103RB 上电默认 HSI **8 MHz**：

```
SYST_RVR = 8_000_000 / 1000 - 1 = 7999
```

⚠ **如果配了 PLL 到 72 MHz，这个值要改成 71999**。
写错的表现是"延时差 9 倍"——和 ch09 波特率算错是同一类错误。

### 1.2 有了 `g_ms` 之后

```c
uint32_t millis(void){ return g_ms; }              /* ISR 和主循环都读 */

/* 非阻塞延时判据（关键：不是"等"，是"问"） */
static uint32_t s_next;
void loop(void){
    if ((int32_t)(millis() - s_next) >= 0) {       /* ← 回绕安全的写法 */
        s_next = millis() + 500u;
        led_toggle();
    }
    do_other_work();                                /* 这行不会被阻塞 */
}
```

**`(int32_t)(millis() - s_next) >= 0` 这个写法是回绕安全的**——
靠 ch04 讲过的 unsigned 回绕。写成 `millis() >= s_next` 在 `s_next` 回绕后会错。
这是嵌入式里最经典的时间比较写法，值得背下来。

## 二、三种"等待"的对比

| 做法 | 代码 | CPU 占用 | 精度 | 适用场景 |
|---|---|---|---|---|
| **忙等循环** | `for(i=0;i<N;i++);` | 100% | 差（随优化变） | 极短的（几微秒）延时 |
| **阻塞延时** | `delay_ms(500);` | 100%（在等） | 好 | 初始化、演示 |
| **非阻塞判据** | `if (millis()-next >= 0)` | **0%** | 好 | **所有正式场合** |

```c
/* ❌ 忙等：优化级别一变，延时长度就变（ch05 实测空循环会被优化掉） */
void delay_bad(uint32_t n){ for (volatile uint32_t i=0;i<n;i++); }

/* ⚠ 阻塞：能用，但期间什么都干不了 */
void delay_ms(uint32_t ms){
    uint32_t start = millis();
    while ((int32_t)(millis() - start) < (int32_t)ms) { }
}

/* ✅ 非阻塞：主循环的"时间片"模式 */
if ((int32_t)(millis() - s_next_blink) >= 0) { ... }
```

**裸机主循环的标准结构**（超级循环 / super-loop）：

```c
int main(void){
    init_all();
    uint32_t t_led = millis(), t_sensor = millis(), t_uart = millis();
    for (;;) {
        uint32_t now = millis();
        if ((int32_t)(now - t_led)    >= 0) { t_led    = now + 500; task_led(); }
        if ((int32_t)(now - t_sensor) >= 0) { t_sensor = now + 10;  task_sensor(); }
        if ((int32_t)(now - t_uart)   >= 0) { t_uart   = now + 1;   task_uart(); }
        /* 还可以进低功耗：__WFI(); */
    }
}
```

这就是**没有 RTOS 的"多任务"**——靠时间片轮询。
它简单、确定、无栈切换开销，代价是：
**任何一个 task 阻塞了，全部 task 都停**（ch20 的 RTOS 就是来解决这个的）。

## 三、通用定时器（TIM2/TIM3…）：比 SysTick 能干

SysTick 只有一个，且分辨率受 OS 心跳限制。
需要**精确波形 / 输入捕获 / PWM** 时用通用定时器。

| 用途 | 用什么 |
|---|---|
| 系统心跳、延时 | **SysTick**（本篇第一节） |
| PWM（调光、电机） | TIMx 的 OC 通道 |
| 输入捕获（测脉宽/频率） | TIMx 的 IC 通道 |
| 精确周期中断（非 1 ms 整数倍） | TIMx 的更新中断 |
| 编码器接口 | TIMx 的 encoder mode |

⚠ **F1 的定时器时钟有个陷阱**：`TIM2` 挂在 APB1，
**当 APB1 预分频系数 ≠ 1 时，定时器的时钟是 PCLK1 × 2**（RM0008）。
所以"以为 36 MHz 其实是 72 MHz"是常见错误——
表现是"PWM 频率差一倍"。

> ⬜ 这部分待 `stm32/06-timer` 实测（用示波器看 PWM 频率验证倍频规则）。

## 四、时间相关的三个经典 Bug

| Bug | 原因 | 对策 |
|---|---|---|
| **延时差 9 倍** | 以为 72 MHz 实际 8 MHz（忘了配 PLL） | 时钟配置完成后**打印/测量确认** |
| **49.7 天后失效** | `uint32_t` 毫秒计数回绕（2^32 ms ≈ 49.7 天） | 用 `(int32_t)(a-b)` 比较法（本篇 1.2） |
| **ISR 里读 millis 读到一半** | `g_ms` 是 32 位，在 8 位/16 位 MCU 上读不是原子的 | Cortex-M3 上 32 位对齐读是原子的，**没问题**；M0 上同样 OK（都是 32 位总线） |

⚠ 但 **`uint64_t` 的毫秒计数在 32 位机上不是原子的**——
如果 ISR 里更新 `uint64_t`，主循环读它时可能被中断打断，读到"半新半旧"。
对策：读的时候关中断，或者用两个 32 位（高/低各一个 volatile）。

## 五、与 PC / LDD- 侧的对照

| 概念 | PC / Linux | 裸机 STM32 |
|---|---|---|
| 时间源 | TSC / HPET / clocksource 框架 | SysTick（内核自带）+ 通用定时器 |
| 获取当前时间 | `clock_gettime()` | `millis()`（自己维护） |
| 延时 | `sleep()` / `nanosleep()`（进程让出 CPU） | 阻塞版占 CPU；非阻塞版靠主循环判据 |
| 定时回调 | `timerfd` / `hrtimer` | 主循环里判时间，或定时器中断 |
| 心跳 | 内核的 `jiffies` / `HZ` | **SysTick 的 `g_ms`** ← 完全对应 |
| 溢出处理 | 内核用 `time_after()` 宏 | `(int32_t)(a-b) >= 0` ← **同一个技巧** |

**内核的 `time_after(a, b)` 就是 `(long)(a) - (long)(b) > 0`**——
和本篇 1.2 的写法一模一样。学两遍，记两遍。

## 六、最小可跑

```c
static volatile uint32_t g_ms;

void SysTick_Handler(void){ g_ms++; }
uint32_t millis(void){ return g_ms; }

/* 回绕安全的时间比较（背下来） */
static inline int time_after(uint32_t a, uint32_t b){
    return (int32_t)(a - b) > 0;
}
static inline int time_after_eq(uint32_t a, uint32_t b){
    return (int32_t)(a - b) >= 0;
}

/* 用法 */
static uint32_t s_deadline;
void start_timeout(uint32_t ms){ s_deadline = millis() + ms; }
int  timed_out(void){ return time_after_eq(millis(), s_deadline); }
```

## 坑点（原书怎么说 / 实际是什么）

| 常识怎么说 | 实际是什么 |
|---|---|
| "写个 `for` 循环就能延时" | 优化级别一变延时就变；ch05 实测**空循环会被整个优化掉**（`wait_bad` → `bx lr`） |
| "`delay_ms(500)` 挺好用" | 期间 CPU 100% 空转，且**其他任务全停**。正式代码用非阻塞判据 |
| "毫秒计数用 `uint32_t` 会溢出" | 会（49.7 天），但**只要用 `(int32_t)(a-b)` 比较就完全安全**（回绕是定义好的，ch04） |
| "SysTick 是 ST 的外设" | **是 ARM 内核的**（`0xE000E010` 在私有外设总线 PPB 上），所有 Cortex-M 都有 |
| "8 MHz 的 F103 上 RVR = 8000" | 是 **7999**（计数包含 0）。差 1 的误差在长跑时会累积 |
| "APB1 上的定时器时钟 = PCLK1" | **APB1 预分频 ≠ 1 时是 PCLK1 × 2**（RM0008）。F1 上 PCLK1=36M 时 TIM2~7 是 72 MHz |
| "SysTick 中断优先级默认就行" | 默认 0（**最高**）。在 RTOS 项目里通常要**调低**（ch10 讲过优先级分配） |

## 衔接

- **ch05（按键）**：去抖要用 SysTick 采样（不再忙等）。
- **ch07（栈帧）**：SysTick 中断会在栈上多压 32 字节，栈预算要算上。
- **ch10（中断）**：SysTick 是最简单的中断，适合当第一个中断实验。
- **ch20（FreeRTOS）**：RTOS 的心跳就是 SysTick；
  `xTaskDelayUntil` 就是本篇非阻塞判据的 RTOS 版。
- **LDD- 侧**：内核的 `jiffies` + `time_after()` 宏，
  和本篇完全同源；`hrtimer` 对应通用定时器。

## 代码自测

<details>
<summary>Q1：为什么 `(int32_t)(millis() - next) >= 0` 是回绕安全的？</summary>

因为 **unsigned 减法回绕是定义良好的**（ch04 实测 `UINT_MAX+1 = 0`），
而且**差值**才是我们关心的量。

设 `a = millis()`、`b = next`，都可能是任意 32 位值。
我们想知道的是"a 是否已经到达或超过 b"。

**关键洞察：`a - b` 的 32 位无符号结果，正好等于"a 领先 b 多少"，
即使 a 或 b 已经回绕过。**

举例（用 8 位简化，回绕点是 256）：

```
b = 250, a = 3        （a 已经回绕过一次，实际领先 9）
a - b = 3 - 250 = -247 → 无符号回绕 → 256 - 247 = 9   ✅ 正确的"领先量"
(int8_t)9 = 9 > 0     → "到达了"      ✅

b = 250, a = 240      （a 还没到，还差 10）
a - b = 240 - 250 = -10 → 无符号回绕 → 246
(int8_t)246 = -10 < 0 → "还没到"      ✅
```

**为什么转成有符号判断**：把 32 位无符号差值重新解释成 `int32_t`，
正数 = "领先"（到达），负数 = "落后"（没到）。
只要"领先量"不超过 `INT32_MAX`（约 24.8 天的毫秒数），这个判断就是正确的。

**对比错误写法**：

```c
if (millis() >= next)          /* ❌ */
```

当 `next` 接近 `0xFFFFFFFF` 而 `millis()` 刚回绕到 0 附近时：

```
next = 0xFFFFFFF0, millis() = 0x00000010    （实际已经过去了 32 ms）
millis() >= next  →  16 >= 4294967280  →  假     ❌ 判断错误！
```

而正确写法：`(int32_t)(0x10 - 0xFFFFFFF0) = (int32_t)0x20 = 32 >= 0` → 真 ✅

**限制**：这个方法能正确处理的最大"落后/领先"是 ±2^31（约 24.8 天）。
超时判据通常远小于这个量级，所以实际永远够用。
**但要小心"下次触发时间"算得太远的情况**——
如果 `next = millis() + 40天`，判断就不可靠了。
</details>

<details>
<summary>Q2：忙等延时为什么不可靠？优化器会做什么？</summary>

三个独立的问题：

**① 优化器可能把整个循环删掉**（ch05 实测）

```c
int flag = 0;
while (flag == 0) { }        /* 非 volatile → 被编译成一条 bx lr */
```

延时循环同理：如果循环变量不是 `volatile`，
编译器会认为"这个循环不改变任何可观察状态"→ 删掉。

**② 就算没被删，指令数也不确定**

```c
for (int i = 0; i < 1000; i++);
```

| 优化级别 | 实际指令数 | 延时（8 MHz） |
|---|---|---|
| `-O0` | 每次迭代 3~5 条 | ~0.5 μs × 1000 = 500 μs |
| `-Os` | 可能被展开/合并 | 完全不同 |
| `-O2` | 可能整个删掉 | 0 |

**同一个源文件换个编译选项，延时就变了**——
这类 bug 的表现是"Debug 版正常，Release 版时序全乱"。

**③ 阻塞期间什么都做不了**

```
delay_ms(500) 期间：
  - 串口来了数据？收不到（ISR 能进，但主循环处理不了）
  - 按键按了？检测不到
  - 看门狗？可能超时复位（如果延时比喂狗周期长）
```

**怎么办**：

| 场景 | 做法 |
|---|---|
| 极短延时（几微秒，如 SPI 片选保持） | 用 `__NOP()` 或数条指令（**并注释说明为什么不精确**） |
| 初始化时的等待（如传感器上电稳定） | 阻塞 `delay_ms()` 可以接受（此时没有别的任务） |
| **运行期的一切延时** | **非阻塞判据**（本篇第二节） |

⚠ 一旦开始阻塞延时，就很容易在中断里也不小心用上——
而 **ISR 里阻塞 = 死锁**（ch10 讲过）。所以从一开始就养成非阻塞的习惯。
</details>

<details>
<summary>Q3：SysTick 属于内核还是芯片厂商？这有什么实际意义？</summary>

**属于 ARM 内核**（Cortex-M 的一部分），不是 ST/NXP/兆易的外设。

证据在地址上：

```
SysTick:  0xE000E010 ~ 0xE000E01C     ← 私有外设总线（PPB，0xE0000000 起）
NVIC:     0xE000E100 ~                ← 同样是内核的
GPIOA:    0x40010800                  ← ST 的外设，在 APB2 上
USART1:   0x40013800                  ← ST 的外设
```

`0xE0000000` 以上是 **ARM 定义的内核私有外设区**，
所有 Cortex-M 芯片都一样；`0x40000000` 是**厂商定义的外设区**，
每家每系列都不同。

**实际意义三条**：

1. **代码可移植**：`SysTick_Config()` 在 STM32、GD32、NXP、瑞萨上**完全一样**。
   换芯片不用改时基代码。
2. **CMSIS 提供了统一封装**：CMSIS-Core 的 `SysTick_Config(ticks)` 一行搞定，
   不用自己写寄存器。
3. **RTOS 依赖它**：FreeRTOS、Zephyr、RT-Thread 的移植层
   都要实现 `SysTick_Handler` / `vPortSetupTimerInterrupt()`——
   **因为它是唯一"所有 Cortex-M 都有"的定时器**。

⚠ 两个细节：

- **SysTick 的时钟源可选**：`CLKSOURCE` 位
  = 1 用 CPU 时钟（F1 上是 HCLK），= 0 用 HCLK/8。
  有些芯片的外部时钟源更准，需要看手册；
- **`SYST_CALIB` 不一定准**：它是"10 ms 校准值"，
  但很多芯片没烧这个值（读到 0）。**不要依赖它**，老老实实按 CPU 频率算。
</details>

<details>
<summary>Q4：我想要"精确周期"的任务（比如每 100 μs 采一次），SysTick 够吗？</summary>

**取决于你的 SysTick 心跳频率和架构。**

SysTick 通常配成 **1 ms**（1 kHz）。
那么 100 μs 的周期用 SysTick 就**做不到**——
你最快只能每 1 ms 检查一次。

**三种解法**：

**① 提高 SysTick 频率**（简单但代价大）

```c
SYST_RVR = cpu_hz / 10000 - 1;      /* 100 μs = 10 kHz */
```

代价：**中断频率提高 10 倍**。10 kHz 的中断，每次进出约 20~30 个周期，
在 8 MHz 下就是 2.5~3.75% 的 CPU 开销，还算可以接受；
但 100 kHz 就占 30% 了——**中断开销会成为瓶颈**。

**② 用通用定时器的更新中断**（推荐）

```c
/* TIM2 配置成 100 μs 周期中断，硬件产生，与 SysTick 独立 */
TIM2_PSC = 0;                    /* 不分频 */
TIM2_ARR = (tim_clk / 10000) - 1;/* 自动重载 = 100 μs */
TIM2_DIER |= (1u << 0);          /* 更新中断使能 */
TIM2_CR1  |= (1u << 0);          /* 启动 */
/* ISR 里做采样，SysTick 继续做 1 ms 系统心跳 */
```

好处：

- **两个时基独立**：1 ms 系统心跳 + 100 μs 采样，互不干扰；
- 定时器是硬件的，**精度由时钟决定，不受中断延迟影响**
  （ISR 响应有抖动，但定时器本身的周期是准的）；
- 还能同时输出 PWM、做输入捕获。

**③ 用 DMA + 定时器触发**（高吞吐）

```
定时器 TRGO → 触发 ADC → ADC 结果由 DMA 直接搬到内存
CPU 完全不参与，只在缓冲区半满/全满时处理一次
```

这是**高频采样的标准做法**（音频、振动监测），
CPU 开销接近零。

**选择判据**：

| 周期 | 方案 |
|---|---|
| ≥ 1 ms | SysTick + 主循环判据（本篇第二节） |
| 100 μs ~ 1 ms | 通用定时器中断（②） |
| < 100 μs 或高频连续 | 定时器 + DMA（③） |
| 需要精确波形输出 | 定时器的 PWM/OC 模式（硬件产生，无软件抖动） |

⚠ **ISR 抖动（jitter）是真实存在的**：
即使定时器周期精确，ISR 的**响应时间**也会因为
"当时正在执行另一个中断/临界区"而推迟几微秒。
需要**严格确定性**的场合（如精确的 PWM 波形），
必须用**硬件输出**（定时器的 OC 通道直接驱动引脚），
不能用"ISR 里翻转 GPIO"。
</details>

<details>
<summary>Q5：没有 RTOS 的超级循环，和 RTOS 比差在哪？</summary>

超级循环（super-loop）就是本篇第二节那个结构：

```c
for (;;) {
    if (time_for_task_a()) task_a();
    if (time_for_task_b()) task_b();
    if (time_for_task_c()) task_c();
}
```

| | 超级循环 | RTOS（ch20） |
|---|---|---|
| 复杂度 | 低（几十行） | 中（要理解调度、同步） |
| RAM 开销 | 极小（共享一个栈） | 每个任务一个栈（几十~几百字节 ×N） |
| Flash 开销 | 0 | 几 KB（内核代码） |
| **阻塞的影响** | **一个 task 阻塞 = 全部阻塞** | 阻塞的任务自动让出 CPU |
| 优先级 | **没有**（按顺序轮询） | 有（高优先级任务抢占） |
| 响应延迟 | 取决于最长的 task | 可预测（优先级决定） |
| 同步原语 | 自己写标志 | 队列/信号量/互斥量现成 |
| 调试 | 简单（单栈） | 复杂（多栈、要查任务状态） |

**什么时候超级循环够用**：

- 任务少（3~5 个）、每个都很短（几十微秒）；
- 没有硬实时要求；
- RAM 极其紧张（F030R8 只有 8 KB）。

**什么时候必须上 RTOS**：

| 信号 | 说明 |
|---|---|
| **有阻塞操作** | 比如"等一个传感器响应 50 ms"——超级循环下这 50 ms 全系统停摆 |
| **任务响应时间要求差异大** | 有的要 1 ms 响应，有的可以 100 ms——需要优先级 |
| **任务间要传数据** | 队列比自己写环形缓冲 + 标志清楚得多 |
| **代码量上千行** | 状态机开始失控，RTOS 的"每个任务顺序执行"更好维护 |
| **团队开发** | 每个人写一个任务，互不干扰 |

⚠ **超级循环的一个隐藏陷阱**：
它假设"每个 task 都会很快返回"。
一旦有人在 `task_c()` 里加了个 `while(等待)`,
整个系统的时序就崩了——而且**症状是"所有功能都变慢"**，
很难定位到具体是哪个 task。

**本仓库的路线**：先写超级循环（理解"时间"怎么造），
再上 FreeRTOS（ch20），
**两相对比才明白 RTOS 到底解决了什么问题**。
直接上 RTOS 只会觉得"它好复杂"，不知道它好在哪。
</details>
