## 本节讲什么

C 的控制语句（`if` / `while` / `for` / `break` / `continue`）本身没什么可讲的，
任何 C 书都讲。这一章对裸机的价值集中在两点：

1. **5.6–5.10「使用按钮」**：第一次读**输入**引脚，
   涉及上拉/下拉电阻这个纯硬件概念——书上讲得到位；
2. **5.14「反模式」**：两个在 PC 上只是"风格不好"、
   在裸机上会变成**死循环或丢中断**的写法。这两条要用反汇编实锤。

## 一、按键：为什么必须有上拉/下拉电阻

书 5.8 讲 *Choosing a Pulldown Circuit*，这是很多人第一次意识到
**"引脚悬空"在物理上是不确定的**。

```
VDD ──┬──[ 10k 上拉 ]──┬── PA0 ──┐
      │                │         │
      │           [ 按键开关 ]────┴── GND
```

| 状态 | 开关 | 引脚电平 | 读到 |
|---|---|---|---|
| 按下 | 闭合 | 直接接 GND | **0** |
| 松开 | 断开 | 经 10k 电阻接到 VDD | **1** |

**关键**：开关断开时，引脚不是"没有连接"，而是**通过 10k 电阻接到了 VDD**。
没有这个电阻，引脚就是天线——实测会读到随机的 0/1（手靠近就变）。

| 电路 | 松开时（idle） | 按下时 | 常见度 |
|---|---|---|---|
| 上拉（pull-**up**） | 1 | 0 | Nucleo 板上最常见，**逻辑是"按下 = 0"** |
| 下拉（pull-**down**） | 0 | 1 | 书里用的是这种 |

STM32 内部就有上拉/下拉电阻（`GPIOx_ODR` 在输入模式下兼任 pupd 选择，F1；
F0/F4 是 `PUPDR` 寄存器），可以省掉外部电阻——
但**板上如果已经焊了外部电阻，就别重复配内部**。

> ⬜ 这部分等 `stm32/05-exti-button` 实测补齐（读 `GPIOA_IDR` 的 bit 0 随按键变化）。
> 本篇不编造未测的数字。

## 二、反模式 1：空 `while` 循环（实锤）

书 5.14.1 说空 `while` 是反模式，但没说**为什么在裸机上致命**。实测：

```c
int flag;                       /* 非 volatile：ISR 改它，主循环看不见 */
volatile int vflag;
void wait_bad(void){ while (flag  == 0) { } }
void wait_ok (void){ while (vflag == 0) { } }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c ch05b.c
$ llvm-objdump -d ch05b.o

00000000 <wait_bad>:
       0: 4770     bx lr          ← 整个等待循环被优化没了！

00000002 <wait_ok>:
       2: movw/movt r0, #0x0      ; &vflag
       a: nop
       c: 6801     ldr  r1, [r0]  ← 循环体内真的读
       e: 2900     cmp  r1, #0
      10: d0fc     beq  0xc
      12: 4770     bx   lr
```

**`wait_bad` 被编译成一条 `bx lr`（直接返回）。**
原因：C11 规定，**没有副作用、也不访问 volatile 对象的无限循环是未定义行为**。
编译器看到 `flag == 0` 这个条件在循环里不会变（它不知道 ISR 会改），
于是有权假定"要么不进循环，要么出不来了"——然后选了最省事的处理。

在裸机上的后果是**程序不等了，直接往下跑**，读到一个还没准备好的寄存器。
加了 `volatile` 的版本（`wait_ok`）才会真的每轮去读。

**结论**：等待硬件标志位的循环，条件里那个变量**必须是 `volatile`**，
而且循环体至少要有个 `nop` 或空语句块 `{}`（别写成 `;` 结尾让人看不出）。

## 三、反模式 2：`while` 条件里的赋值

书 5.14.2 讲 `while (ch = getchar())` 这类写法。实测编译器的反应：

```
$ clang -Wall -Wextra -c ch05.c
ch05.c:10:17: warning: using the result of an assignment as a condition without parentheses [-Wparentheses]
   10 |     while (*d++ = *s++) ;
      |            ~~~~~^~~~~~
```

`while (*d++ = *s++);` 是经典 `strcpy` 实现，它**能工作**（实测输出 `"hi"`），
但问题是：

1. **`=` 和 `==` 打错时编译器未必能救你**——加了括号 `-Wparentheses` 就不报了，
   于是 `while (x = 0)`（本意 `== 0`）会静默变成"永远不进循环"；
2. 把赋值和判断挤在一行，读代码的人要停一下才能理清执行顺序。

推荐写法（实测等价）：

```c
while ((*d = *s) != '\0') { d++; s++; }    /* 意图明确，编译器不再警告 */
```

裸机上的延伸：**按键去抖**别写成"忙等 + 空循环"，
要么用定时器（ch19 的 SysTick）采样，要么在中断里打时间戳——
忙等会白白烧掉 CPU 和电。

## 四、与 PC / LDD- 侧的对照

| 概念 | PC / Linux | 裸机 STM32 |
|---|---|---|
| 等待事件 | 阻塞 syscall（`read()` 睡在内核里，CPU 让给别人） | 只能轮询（`while`）或进 WFI 低功耗（ch19） |
| 空循环等待 | 通常无害，只是浪费 | **可能被优化成不存在**（实测 `wait_bad` → `bx lr`） |
| 按键 | `/dev/input/eventX` + 内核去抖 | 自己读 `IDR`，自己去抖 |
| 去抖 | 驱动/tty 层做 | 你做（延时重采样 / 定时器 / 状态机） |
| `break`/`continue` | 纯语法 | 同；但在 ISR 里用 `break` 要小心别跳过清理动作 |

## 五、最小可跑

```c
typedef unsigned int u32;
#define GPIOA_CRL (*(volatile u32 *)0x40010800u)
#define GPIOA_IDR (*(volatile u32 *)0x40010808u)
#define RCC_APB2ENR (*(volatile u32 *)0x40021018u)

/* PA0 配成输入 + 上拉（F1：CNF=10 表示上/下拉输入，ODR 位决定上还是下） */
void button_init(void){
    RCC_APB2ENR |= (1u << 2);          /* ① 开时钟，永远是第一步 */
    GPIOA_CRL &= ~(0xFu << 0);         /* ② 清 PA0 的 4 位 */
    GPIOA_CRL |=  (0x8u << 0);         /*    CNF=10(上/下拉输入) MODE=00(输入) */
    /* F1 上：输入模式下 ODR 的对应位 = 1 选上拉，= 0 选下拉 */
    *(volatile u32 *)0x4001080Cu |= (1u << 0);   /* 上拉 */
}

int button_pressed(void){              /* 上拉逻辑：按下 = 0 */
    return (GPIOA_IDR & (1u << 0)) == 0;
}

/* 轮询 + 软件去抖：连续读到 N 次相同才算数 */
int button_pressed_debounced(void){
    int hits = 0;
    for (int i = 0; i < 20; i++) {
        if (button_pressed()) hits++;
        /* 真实代码这里要有 ~1ms 延时（ch19 的 SysTick） */
    }
    return hits > 15;
}
```

## 坑点（原书怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| 书 5.14.1：空 `while` 是反模式（风格问题） | 裸机上是**正确性问题**：实测 `while (flag == 0) {}` 被编译成 `bx lr`（循环整个消失）。条件变量必须 `volatile` |
| "按键按下读到 1" | 取决于电路。上拉时**按下读 0**（实测要按板子原理图确认）；书里用的是下拉，按下读 1 |
| "不接电阻也能读" | 引脚悬空时电平不确定（天线效应），实测会随机跳变。必须上拉或下拉 |
| "STM32 内部有上/下拉就够" | 板子如果已焊外部电阻，别重复配；F1 上要靠 `ODR` 位选上/下拉，容易漏配成"浮空输入" |
| "按键去抖写个 `for(i=0;i<10000;i++);` 就行" | 忙等烧 CPU + 延时不准（取决于编译优化和主频）。用 SysTick（ch19）或状态机 |
| `while (x = f())` 挺简洁 | 实测 `-Wparentheses` 会警告；加括号后警告消失，`=` / `==` 打错就没人管了 |
| "循环条件里做 I/O 很方便" | 裸机寄存器读取有副作用（`volatile`），塞进条件里会让"每轮读几次"变得不直观 |

## 衔接

- **ch06（数组、指针、字符串）**：`button_pressed_debounced` 里那个 `for` 循环，
  第 6 章会把它改成环形缓冲的历史采样。
- **ch10（中断）**：轮询按键只是过渡方案。真正的产品用 EXTI 中断 + ISR 里置标志，
  主循环再去处理——那时本章的 `volatile flag` 就成了核心机制。
- **ch19（SysTick / 定时器）**：去抖和延时都需要"时间"，裸机上时间靠 SysTick。
- **LDD- 侧**：Linux 的按键走 `input` 子系统 + 中断线程化 + 内核去抖；
  裸机上这些全是你自己的活，正好理解内核替你做了多少。

## 代码自测

<details>
<summary>Q1：为什么 `wait_bad` 会被编译成一条 `bx lr`？这不是编译器的 bug 吗？</summary>

不是 bug，是标准允许的。

C11 §6.8.5p6 有一条脚注式规定：**如果循环的条件表达式不是常量，
且循环体不执行 I/O、不访问 volatile 对象、不做同步操作，
编译器可以假定这个循环会终止**。反过来——如果编译器能证明它**不会**终止，
那这个程序就踏进了未定义行为（UB），编译器想怎么处理都行。

我们的例子里：

```c
int flag;                       /* 初值 0，非 volatile */
void wait_bad(void){ while (flag == 0) { } }
```

编译器推理链是：`flag` 初值是 0 → 条件 `flag == 0` 为真 → 进循环 →
循环体什么都不做、也没人改 `flag` → **永远出不来** → 这是 UB →
那我随便生成什么都可以 → 生成一条 `bx lr`（最快）。

**它不知道 ISR 会在运行时改 `flag`。** 加了 `volatile` 之后，
`vflag` 的每次读取都是"可观察行为"，循环体不再是无副作用的，
编译器必须老老实实每轮读——实测 `wait_ok` 里确实有 `ldr r1, [r0]`。

一句话：**`volatile` 不是在告诉编译器"这个值会变"，
是在告诉它"每次都必须真的去读，不许替我推理"。**
</details>

<details>
<summary>Q2：上拉和下拉，我该选哪个？</summary>

看两件事：**板上已经焊了什么**，以及**你希望"没动作"时读到什么**。

| | 上拉（pull-up） | 下拉（pull-down） |
|---|---|---|
| 空闲电平 | 1 | 0 |
| 按下电平 | 0 | 1 |
| 代码 | `return (IDR & BIT) == 0;` | `return (IDR & BIT) != 0;` |
| 抗干扰 | 略好（工业现场常用，断线会被读成"按下"，fail-safe） | 断线读成"没按"，可能掩盖故障 |

工程上的选择顺序：

1. **先看原理图**。NUCLEO-F103RB 的用户按键（如果有）和板上跳线决定了一切，
   猜是没用的。
2. **如果没有外部电阻**，用 STM32 内部的（F1 通过 `ODR` 位在输入模式下选择，
   F0/F4 用 `PUPDR` 寄存器）——省一个元件。
3. **安全相关**的场合选上拉：断线/接触不良会被读成"按下"（显性故障），
   而不是"没按"（隐性故障）。这和工业 PLC 的惯例一致。

书里用下拉（所以它的代码是"按下读到 1"），本仓库的板子要按原理图确认——
这也是为什么本篇的代码上方标注了 ⬜ 待实测。
</details>

<details>
<summary>Q3：按键去抖到底在抖什么？</summary>

机械触点闭合/断开时，金属弹片会在**几毫秒内物理弹跳多次**，
电平在 0/1 之间来回跳十几次才稳定。示波器上看是一串毛刺。

如果你不去抖，一次按键可能被读成 5 次按下——
表现为"按一下，LED 状态翻了好几回"或者"菜单跳了好几项"。

三种做法，按推荐度排序：

| 做法 | 思路 | 代价 |
|---|---|---|
| **定时器采样**（推荐） | SysTick 每 1 ms 采一次，连续 N 次（如 20 次）相同才认定状态改变 | 需要一个时基（ch19） |
| **中断 + 时间戳** | 边沿触发 ISR，ISR 里记 `last_tick`，主循环里判断距上次 > 20 ms 才响应 | 需要 EXTI（ch10）+ 时基 |
| **忙等延时**（最差） | 读到变化后 `delay_ms(20)` 再读一次 | 阻塞 CPU、延时不准、期间丢事件 |

书里用的是最简单的忙等（教学够用）。工程上**不要**用——
它会让 CPU 在 20 ms 里什么都干不了，而且 `-O0` 和 `-Os` 下延时长度还不一样
（实测：空循环的指令数随优化级别变化）。
</details>

<details>
<summary>Q4：`break` 和 `continue` 在 ISR 里有什么特别的坑？</summary>

语法上没坑，但**语义上有个要命的陷阱：ISR 里的 `break` 可能跳过清理动作。**

典型翻车：

```c
void USART1_IRQHandler(void){
    if (!(USART1_SR & RXNE)) return;      /* 提前返回：还行，只是没做事 */
    ...
    if (buf_full) break;                  /* 跳出循环 */
    ...
    USART1_SR &= ~RXNE;                   /* 清中断标志 —— 被跳过了！ */
}
```

清中断标志一定要做，否则 **ISR 会立刻被重新触发**（标志还在），
表现为"程序卡死在中断里，主循环再也不跑"。

防御写法：

1. **单一出口**：ISR 里不用 `break`/`return` 提前跳，用 `if/else` 走到最后统一清理；
2. 或者用 `goto cleanup;` 集中到一个清理标签；
3. 或者最稳的：**先清标志，再干活**（读 SR → 清标志 → 处理数据），
   这样无论后面怎么跳，标志都已经清了。

这个坑属于"中断"的范畴，ch10 会展开。这里先记住一句：
**在裸机 ISR 里，`break` 不只是控制流，它可能意味着"没清中断标志"。**
</details>

<details>
<summary>Q5：书 5.14 只列了两个反模式，还有哪些是我该一开始就避开的？</summary>

补三条在裸机上代价特别高的：

1. **在循环条件里调用有副作用的函数**
   `while (uart_getchar() != '\n')` —— 每次判断都会真的读一次串口，
   数据就被吃掉了。应该 `int c; while ((c = uart_getchar()) != '\n')` 或者先读再用。
2. **用浮点做循环变量**
   `for (float f = 0; f < 1.0; f += 0.1)` —— 实测 `0.1` 累加 10 次得到
   `1.00000011920928955078`（见 ch16），循环次数会和你想的不一样。
   而且 M0/M3 没有 FPU，浮点是软件模拟的，慢几个数量级。
3. **依赖"循环体为空"来做延时**
   `for (int i=0;i<1000;i++);` —— 实测这类空循环在 `-Os` 下可能被整个删掉
   （和本章 `wait_bad` 一个道理）。要延时就用 SysTick 或定时器，
   或者至少把循环变量声明成 `volatile`。

共同的本质：**裸机上"看起来能跑"和"真的按你想的跑"之间，
隔着一个优化器。** 所以凡是涉及"等硬件""数时间""读两次"的代码，
都要问一句：编译器有没有权力把它改掉？
</details>
