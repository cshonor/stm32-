# ch16 · 浮点数：为什么 M0/M3 上要慎之又慎

> 对应实验：主机侧实测（clang 23.1.0，macOS）
> 对应书：**第 16 章 浮点数**（16.1 数字表示 / 16.2 舍入误差 /
> 16.3 精度位数 / 16.4 无穷大 / 16.5 不是数字（NaN）/ 16.6 次正规数 /
> 16.7 替代方案）

## 本节讲什么

书把浮点放在第二部分"用于大型机器的 C 语言编程"里，
**是因为书里的板子 NUCLEO-F030R8 是 Cortex-M0——没有 FPU**。
在 M0 上做浮点是**软件模拟**的，慢得离谱，
所以作者干脆把它挪到"大型机器"部分讲。

这本身就是一个重要结论：**在你确定芯片有 FPU 之前，不要假设浮点是便宜的。**

本篇实测浮点数的三个反直觉行为，然后讲裸机上该怎么办。

## 一、实测：浮点数的三个"不对"

```
$ clang -O0 -o ch16 ch16.c && ./ch16
sizeof float=4 double=8 ; FLT_DIG=6 DBL_DIG=15
FLT_EPSILON=1.19209e-07  DBL_EPSILON=2.22045e-16
0.1 + 0.2 = 0.30000000000000004441  (== 0.3 ? 否)
1e20 + 1 == 1e20 ? 是  ← 大数吃小数
0.1 累加 10 次 = 1.00000011920928955078
0.0/0.0 = nan (NaN, NaN!=NaN: 是)
1.0/0.0 = inf
1e-320 (次正规) = 9.99989e-321
0.1f 的 IEEE-754 位模式 = 0x3dcccccd (sign/exp/frac)
```

### 1.1 `0.1 + 0.2 != 0.3`（实测"否"）

不是 bug，是**二进制无法精确表示十进制的 0.1**。

```
0.1 (十进制) = 0.000110011001100110011... (二进制，无限循环)
```

浮点只能存有限位，所以存的是一个近似值。两个近似值相加，
结果和 `0.3` 的近似值不相等。

**正确的比较方式**：

```c
/* ❌ 错 */
if (x == 0.3) { ... }

/* ✅ 对：比较差值 */
#include <math.h>
if (fabs(x - 0.3) < 1e-9) { ... }

/* ✅ 更好：相对误差（适合量级变化大的场景） */
int nearly_equal(double a, double b, double rel_tol){
    double diff = fabs(a - b);
    double scale = fabs(a) > fabs(b) ? fabs(a) : fabs(b);
    return diff <= scale * rel_tol;      /* rel_tol 如 1e-9 */
}
```

实测的 `FLT_EPSILON = 1.19209e-07` 是"1.0 和下一个可表示数的差"，
它**不是**万能的容差——大数的间隔更大。

### 1.2 大数吃小数（实测"是"）

```
1e20 + 1 == 1e20 ? 是
```

`1e20` 的有效位只有约 15~17 位十进制（`DBL_DIG=15` 实测），
加 1 完全落在精度之外，直接被舍掉。

**工程后果**：累加时要**从小到大**加，或者用 Kahan 补偿求和。
传感器数据平滑、积分运算都会遇到。

### 1.3 `NaN != NaN`（实测"是"）

```
0.0/0.0 = nan (NaN, NaN!=NaN: 是)
```

NaN 和自己都不相等——这是 IEEE-754 的定义。
所以 `if (x == x)` 是**检测 NaN 的经典写法**（不是笔误）。

```c
if (x != x) { /* x 是 NaN */ }
/* 或用 <math.h> 的 isnan(x)，更清楚 */
```

⚠ 裸机 freestanding 下没有 `<math.h>`（ch01 实测只有 7 个头），
所以要自己判断：`x != x`。

### 1.4 次正规数（denormal）

```
1e-320 (次正规) = 9.99989e-321
```

正常 double 的最小正规数约 `2.2e-308`。
比它更小的数只能用"次正规"表示——**精度会急剧下降**
（有效位变少）。而且很多 MCU 的 FPU 处理次正规数**极慢**（甚至有 trap）。

**工程结论**：如果你的计算会产生接近零的数，
要么加一个小的偏置避免进入次正规区，要么用定点数。

## 二、位级看浮点（实测）

```
0.1f 的 IEEE-754 位模式 = 0x3dcccccd
```

拆开（float，1 符号 + 8 指数 + 23 尾数）：

```
0x3dcccccd = 0 01111011 10011001100110011001101
             │ │        │
             │ │        └─ 尾数（23 位）：1.10011001100110011001101
             │ └────────── 指数（8 位）：0x7B = 123 → 实际指数 = 123 - 127 = -4
             └──────────── 符号：0（正）

值 = 1.6000000238418579 × 2^-4 = 0.10000000149011612
```

**不是精确的 0.1**，是 `0.10000000149...`。这就是 1.1 节那个"不对"的物理原因。

裸机上这个技巧很有用：

```c
/* 协议里传浮点：按位模式传 4 字节，避免格式化 */
typedef union { float f; uint32_t u; } fbits_t;
fbits_t v = { .f = sensor_value };
send_u32(v.u);          /* 精确、快、只有 4 字节 */
```

比 `printf("%f")` 快几个数量级（ch09/ch14 讲过 `%f` 是最贵的格式）。

## 三、裸机上该不该用浮点？

决策表：

| 芯片 | FPU | 建议 |
|---|---|---|
| **Cortex-M0 / M0+（如 F030R8）** | **无** | **能不用就不用**。`float` 加减是几十条指令，`double` 几百条 |
| **Cortex-M3（如 F103RB）** | **无** | 同上。ch01 实测符号表里的 `__aeabi_dadd`/`__aeabi_dmul` 就是证据 |
| **Cortex-M4F / M7（如 F407）** | **有（单精度）** | `float` 硬件加速（单周期），**`double` 仍是软件** |
| Cortex-M7（双精度版） | 有（双精度） | `double` 也快 |

⚠ **即使有 FPU，也要注意**：

1. **FPU 默认可能是关闭的**（M4 上要设 `SCB->CPACR` 使能），
   没开就用浮点 → **HardFault 或 UsageFault**；
2. **`double` 在单精度 FPU 上仍是软件模拟**（慢）；
3. **用 FPU 会让中断帧多压 136 字节**（M4 的浮点上下文），
   栈预算要加（ch07 讲过栈预算）；
4. **printf 的 `%f` 需要 newlib 的浮点支持**，Flash 占用会涨。

ch01 的实测就是 M3 上的证据：

```
U __aeabi_dadd        ← 浮点乘加，M3 没有 FPU，走软件浮点
U __aeabi_dmul
```

## 四、替代方案（书 16.7）

**定点数（fixed-point）** 是嵌入式的经典答案：

```c
/* Q16.16：高 16 位整数部分，低 16 位小数部分 */
typedef int32_t q16_t;
#define Q16_SHIFT 16
#define FLOAT_TO_Q16(f)  ((q16_t)((f) * 65536.0f))
#define Q16_TO_FLOAT(q)  ((float)(q) / 65536.0f)

static inline q16_t q16_add(q16_t a, q16_t b){ return a + b; }       /* 整数加法！ */
static inline q16_t q16_mul(q16_t a, q16_t b){ return (q16_t)(((int64_t)a * b) >> Q16_SHIFT); }
```

| | 浮点 | 定点 |
|---|---|---|
| 速度（M0/M3） | 慢（软件模拟） | **快**（整数指令） |
| 确定性 | 有次正规等特殊情况 | **完全确定** |
| 动态范围 | 大（`1e-38` ~ `1e38`） | 小（Q16.16 只有 ±32768） |
| 代码大小 | 要链接软浮点库（几 KB） | 几行 inline |
| 精度 | 相对精度恒定 | 绝对精度恒定 |

**其他替代**：

| 场景 | 方案 |
|---|---|
| 温度、电压等物理量 | **整数 + 固定倍率**（`int32_t temp_mC` 表示毫摄氏度） |
| PID 控制 | 定点数 |
| 显示 | 整数拆分（`2345` → `"23.45"`），不用 `%f` |
| 协议传输 | 定点的整数位模式（快且精确） |
| 真的需要大范围 | 用 `float` 但限定在计算密集的少数几处 |

**本仓库的取向**：物理量一律用"整数 + 单位后缀命名"
（`temp_mC`、`volt_mV`、`freq_cHz`），
只在极少数地方用 `float`（且要确认芯片有 FPU）。

## 五、与 PC / LDD- 侧的对照

| 概念 | PC / Linux | 裸机 STM32 |
|---|---|---|
| FPU | 有，默认开 | M0/M3 **没有**；M4F 有单精度但要手动使能 |
| `double` | 硬件加速 | M4F 上仍是**软件**（ch01 实测 `__aeabi_dadd`） |
| `%f` | 便宜 | **很贵**（软件格式化 + 软件浮点） |
| `isnan()` | `<math.h>` | freestanding 没有 `<math.h>`，用 `x != x` |
| 中断帧 | 无影响 | 用 FPU 时**多压 136 字节**（M4） |

## 六、最小可跑

```c
/* 主机侧：验证浮点行为 */
printf("0.1+0.2 == 0.3 ? %s\n", (0.1+0.2==0.3) ? "是" : "否");   /* 否 */
printf("NaN != NaN ? %s\n", ((0.0/0.0) != (0.0/0.0)) ? "是" : "否"); /* 是 */

/* 裸机侧：物理量用整数 */
static int32_t g_temp_mC;        /* 毫摄氏度：23450 = 23.45 ℃ */

void print_temp(int32_t mC){
    int ip = mC / 1000, fp = mC % 1000;
    if (fp < 0) fp = -fp;
    mini_printf("%d.%03d C\r\n", ip, fp);    /* 不用 %f */
}
```

## 坑点（原书怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "`0.1 + 0.2 == 0.3`" | **否**。实测 `0.1+0.2 = 0.30000000000000004441` |
| "浮点数精度很高" | `FLT_DIG=6`（float 只有 6 位可靠十进制）、`DBL_DIG=15`（实测） |
| "`x == x` 恒成立" | NaN 不满足。实测 `NaN != NaN` 为"是"——这正是检测 NaN 的方法 |
| "用 `float` 省空间" | 省 RAM（4 字节 vs 8），但在**没有 FPU 的 M0/M3 上不省时间**（软件模拟） |
| "M4 有 FPU，随便用浮点" | ① 要使能 `SCB->CPACR`，否则 HardFault；② **`double` 仍是软件**；③ 中断帧 +136 字节 |
| "次正规数是边缘情况" | 实测 `1e-320` 能用，但**精度骤降且可能极慢**。算法要避开接近零的区间 |
| "`printf("%f")` 方便" | 最贵的格式（ch14）。裸机上用整数拆分打印 |
| "定点数很麻烦" | Q 格式只有加/减/乘/除四个 inline 函数，比链接软浮点库简单得多 |

## 衔接

- **ch04（数字）**：整数是精确的、位模式确定的；浮点是近似的——
  这个对比是选择数据类型的基础。
- **ch08（复杂类型）**：union 拆浮点位模式（实测 `0.1f = 0x3dcccccd`）。
- **ch09（串口）**：`%f` 是最贵的格式，协议里传位模式而不是格式化字符串。
- **ch19（SysTick）**：PID 控制常用定点数，因为控制循环有硬实时要求。
- **LDD- 侧**：**内核里默认禁用浮点**（要 `kernel_fpu_begin/end`）——
  和裸机的"谨慎使用"是同一个理由：上下文切换要保存 FPU 寄存器，代价高。

<details>
<summary>Q1：`0.1 + 0.2` 为什么不等于 `0.3`？这是我代码的问题吗？</summary>

不是你代码的问题，是**二进制表示的根本限制**。

```
0.1 (十进制) 转成二进制 = 0.0001100110011001100110011...  （无限循环）
0.2 (十进制) 转成二进制 = 0.0011001100110011001100110...  （无限循环）
```

`float`/`double` 只有有限的尾数位（23 / 52 位），
所以存的是**截断后的近似值**。两个近似值相加，
结果和"0.3 的近似值"不完全相等。

实测：

```
0.1 + 0.2 = 0.30000000000000004441  (== 0.3 ? 否)
```

**类比**：十进制里 `1/3 = 0.333...`，
`3 × 0.333 = 0.999 ≠ 1`——同样的道理，只是发生在二进制上。

**怎么处理**：

```c
/* ① 绝对容差（量级已知时） */
if (fabs(x - 0.3) < 1e-9) { ... }

/* ② 相对容差（量级变化大时） */
static int nearly_eq(double a, double b, double rel){
    double s = fabs(a) > fabs(b) ? fabs(a) : fabs(b);
    return fabs(a - b) <= s * rel;
}

/* ③ 干脆用整数（嵌入式首选） */
int32_t cents = ...;      /* 用"分"而不是"元" */
```

⚠ **不要用 `FLT_EPSILON` 当万能容差**：
实测 `FLT_EPSILON = 1.19209e-07`，它是"1.0 附近的间隔"。
对于 `1e20` 这样的数，间隔要大得多（实测 `1e20 + 1 == 1e20`）——
绝对容差在那里完全失效，必须用相对容差。
</details>

<details>
<summary>Q2：Cortex-M3（我的 F103RB）上用浮点到底多慢？</summary>

**没有 FPU，全是软件模拟。** ch01 的实测就是证据：

```
$ make check-libc        # stm32/00-toolchain-clang
U __aeabi_dadd      ← 浮点乘加，M3 没有 FPU，走软件浮点
U __aeabi_dmul
```

`U` 表示"未定义符号"——编译器生成的是**对库函数的调用**，不是几条指令。
这些 `__aeabi_*` 函数来自 libgcc/compiler-rt，每个都是几十到几百条指令。

**量级估计**（8 MHz 的 F103，软件浮点）：

| 运算 | 大致周期数 | 时间 @ 8 MHz |
|---|---|---|
| `float` 加/减 | ~50–100 | 6–12 μs |
| `float` 乘 | ~50–100 | 6–12 μs |
| **`float` 除** | ~100–300 | 12–37 μs |
| **`double` 加/乘** | ~200–500 | 25–62 μs |
| **`double` 除** | ~500–1000+ | 62–125 μs |
| **整数加/乘** | 1 | 0.125 μs |

**所以一次 `double` 除法 ≈ 1000 次整数加法。**

后果：

- 在 1 kHz 的控制循环（1 ms 预算）里，几十次 `double` 运算就用光了预算；
- 在 ISR 里用浮点 = 灾难（ch10 讲过 ISR 要快）；
- `printf("%f")` 会把软浮点库 + 格式化库都拉进来，**Flash 涨几 KB**
  （ch11 讲过 Flash 预算）。

**对策**：

1. **优先用整数表示物理量**（`temp_mC`、`volt_mV`）；
2. 需要小数运算时用**定点数**（本篇第四节）；
3. 非用 `float` 不可时，**绝不用 `double`**（`float` 的软件实现比 `double` 快得多）；
4. 把浮点运算**集中在少数非实时的地方**（初始化时算系数，运行期只用整数）。

**F407（M4F）的对照**：有单精度 FPU，
`float` 加减乘是**单周期**——快 100 倍。
但 `double` 仍然是软件的。所以用 `float` 而不是 `double`，在 M4F 上依然重要。
</details>

<details>
<summary>Q3：M4/M7 有 FPU，为什么用了浮点还是会 HardFault？</summary>

最常见的原因：**FPU 没有使能**。

Cortex-M4F 上电后，**FPU 默认是关闭的**（为了兼容和不用的场景省电）。
要使能它，必须设置协处理器访问控制寄存器 `SCB->CPACR`：

```c
/* 使能 FPU（M4F）：CP10 和 CP11 都设为"完全访问" */
SCB->CPACR |= ((3UL << 10*2) | (3UL << 11*2));   /* CP10=CP11=0b11 */
__DSB(); __ISB();      /* 屏障：确保设置生效后再用浮点 */
```

没做这一步就执行浮点指令 → **UsageFault（NOCP：No Coprocessor）**。

在 STM32 上，如果你用厂商的 HAL/启动代码，这一步通常在
`SystemInit()` 里做了；**自己写裸机启动时必须自己做**（本仓库的情况）。

**其他导致浮点 HardFault 的原因**：

| 原因 | 说明 |
|---|---|
| **中断帧变大** | 用 FPU 后，中断时硬件要多压 17 个浮点寄存器（68 字节），
  加上对齐可能是 136 字节。**栈不够就溢出**（ch07） |
| **栈溢出** | 同上，且栈溢出在裸机上是静默的 |
| **未对齐访问** | `double` 要求 8 字节对齐（M0 不支持未对齐，M3/M4 支持但慢） |
| **在 ISR 里用 `double`** | 慢 + 栈开销大，间接导致丢中断 |

**排查清单**：

1. `SCB->CPACR` 设了没？（gdb 里 `x/1xw 0xE000ED88` 看是否为 `0x00F00000`）；
2. 栈够不够？（ch07 的 `-fstack-usage` + 中断帧 136 字节）；
3. 用了 `double` 吗？（M4F 上 `double` 是软件的，慢但不会 HardFault）；
4. `-mfloat-abi` 对不对？（`soft` / `softfp` / `hard`，
   要和库的一致性匹配，混用会导致 ABI 不兼容）。
</details>

<details>
<summary>Q4：定点数怎么写？会不会很麻烦？</summary>

核心只有四个 inline 函数，比你想的简单。

**Q 格式的含义**：`Qm.n` 表示 m 位整数部分、n 位小数部分。
最常用的是 **Q16.16**（`int32_t`，16 位整数 + 16 位小数）：

```c
typedef int32_t q16_t;                 /* 范围 ±32768，精度 1/65536 ≈ 1.5e-5 */

/* 转换 */
#define Q16_FROM_INT(i)   ((q16_t)(i) << 16)
#define Q16_TO_INT(q)     ((q16_t)(q) >> 16)
#define Q16_FROM_FLOAT(f) ((q16_t)((f) * 65536.0f))
#define Q16_TO_FLOAT(q)   ((float)(q) / 65536.0f)

/* 四则运算 */
static inline q16_t q16_add(q16_t a, q16_t b){ return a + b; }   /* 就是整数加 */
static inline q16_t q16_sub(q16_t a, q16_t b){ return a - b; }
static inline q16_t q16_mul(q16_t a, q16_t b){
    return (q16_t)(((int64_t)a * (int64_t)b) >> 16);             /* 注意 64 位中间 */
}
static inline q16_t q16_div(q16_t a, q16_t b){
    return (q16_t)(((int64_t)a << 16) / b);
}
```

**两个易错点**：

1. **乘法必须用 64 位中间值**。`a * b` 在 32 位上会溢出
   （两个 Q16.16 相乘，中间结果是 Q32.32）。
   用 `int64_t` 中转再右移 16 位。
   ⚠ 在 M0/M3 上 `int64_t` 运算也是软件的——所以**乘法才是定点的真正成本**，
   加减法完全免费。
2. **除法要先左移再除**，`(a << 16) / b`，否则精度全丢。

**什么时候麻烦**：

- 需要**大动态范围**（既有 1e-6 又有 1e6）——定点做不到；
- 需要 `sqrt` / `sin` / `log`——要自己写查表或级数；
- 需要**相对精度恒定**（定点是绝对精度恒定）。

**什么时候特别合适**（嵌入式的绝大多数场景）：

- 物理量范围已知（温度 -40~125℃、电压 0~3.3V）；
- PID 控制、滤波、平均；
- 需要**确定性**（硬实时，浮点有次正规等特殊情况耗时不定）。

**简化技巧**：如果范围更清楚，可以用更简单的格式。
比如温度用 `int16_t` 存"0.1℃"`（`-400` = -40.0℃）——
**根本不需要 Q 格式的库函数**，就是整数加一个"单位约定"。
这往往是最实用的做法。
</details>

<details>
<summary>Q5：我要把浮点通过串口/协议发出去，怎么发最好？</summary>

三种方式，按推荐度：

**① 传位模式（4 字节，精确，快）**

```c
typedef union { float f; uint32_t u; } fbits_t;
fbits_t v = { .f = sensor };
send_bytes((const uint8_t *)&v.u, 4);     /* 注意字节序！ */
```

- 精确（位级无损）；
- 快（就是发 4 个字节）；
- 但**接收方必须是同样的 IEEE-754 格式和字节序**。

实测 `0.1f` 的位模式是 `0x3dcccccd`——这就是要发的 4 个字节
（小端序下是 `cd cc cc 3d`）。

**② 传定点整数（最推荐，跨平台）**

```c
int32_t temp_mC = 23450;          /* 23.450 ℃ */
send_u32_le((uint32_t)temp_mC);
```

- 精确、跨平台、可读（调试时直接看数字）；
- 接收方只要知道单位（毫摄氏度）就行；
- 不受浮点格式/字节序差异影响。

**③ 传格式化字符串（最慢，但人可读）**

```c
mini_printf("%.2f", temp);       /* "23.45" —— 5 字节 + 格式化开销 */
```

- 人能直接读（调试友好）；
- 但**慢**（格式化 + 软浮点）、**冗长**、精度损失（只有 2 位）。

**选择建议**：

| 场景 | 方式 |
|---|---|
| 调试日志 | ③（人要看）+ ①/② 都行 |
| 设备间协议（都是 Cortex-M） | ① 或 ② |
| 设备间协议（跨平台/跨语言） | **②**（定点整数，无歧义） |
| 高频数据（如 IMU 采样流） | **②**（快、定长） |

⚠ **无论哪种，都要定义字节序**。
实测 Cortex-M 是小端（`0x12345678 → b[0]=0x78`，ch08），
x86/arm64 也是小端，但**协议里要写明白**，
并且用显式的 `send_u32_le()` 而不是直接发内存
（ch08 Q3 讲过按字节拼装的必要性）。
</details>
